## Working rules
1. You work in your own worktree on branch `story/{{.ID}}`, cut from `epic/{{.Slug}}` (or the owner branch named under
   "Shared files"). Plan with `ak-plan` against current HEAD, {{if eq .Delivery.Style "pipo"}}keep the plan dir local (it
   is in `.git/info/exclude`, never committed into the PR){{else}}commit the plan dir{{end}}, then
   `orca orchestration ask --question "plan ready, ok to implement?" --timeout-ms 3600000` (terminal plane: `cox story
   report question --body "plan ready, ok to implement?"` then `cox question wait <qNNN> --max 60m`, rule 9) and wait. Do not create or edit
   any other file until the reply arrives.
{{if eq .Delivery.Style "pipo"}}2. On approval: implement with `ak-cook`, one phase = one commit ending with the trailer `Phase: N/M`; a fix to an
   earlier phase is a `fixup!` commit. COMMITS STAY LOCAL - do not push until the story is done and green.
{{else}}2. On approval: push `story/{{.ID}}` and open a DRAFT PR into `epic/{{.Slug}}` (`gh pr create --draft`) with the plan's
   phase list as the body. Implement with `ak-cook`, one phase = one commit ending with the trailer `Phase: N/M`; a fix to
   an earlier phase is a `fixup!` commit. Push at the end of every phase.
{{end}}3. Tests per phase land the "Verification" suites for what the phase built and run through one script per step. Golden
   baselines are generated by the suite's own runner, never by hand, and reviewed as diffs. LOOK at every frame you
   capture; a capture script saves a frame only when its flow exited 0 (workflow ruling 2026-09-02, the earlier "no PNG"
   rule is withdrawn).
{{if eq .Delivery.Style "pipo"}}4. Ready: `git fetch origin && git rebase --autosquash origin/epic/{{.Slug}}` (resolve, re-run the gates), then ONE push
   of `story/{{.ID}}`, and open the PR READY (not draft) into `epic/{{.Slug}}`. Then
   `orca orchestration ask --question "PR <url> ready for review; anything to change before I report done?" --timeout-ms 3600000` (terminal plane: `cox story report question` + `cox question wait`, rule 9)
   and wait. Only after the leader replies `released` send `worker_done` with the PR URL.
{{else}}4. Ready: `git fetch origin && git rebase --autosquash origin/epic/{{.Slug}}` (resolve, re-run the gates), push, mark
   the PR ready, then
   `orca orchestration ask --question "PR <url> ready for review; anything to change before I report done?" --timeout-ms 3600000` (terminal plane: `cox story report question` + `cox question wait`, rule 9)
   and wait. Only after the leader replies `released` send `worker_done` with the PR URL.
{{end}}5. Compaction at a phase boundary: when `cox checkpoint facts` (or the watcher) says you are near {{.Context.PlanCompact}}
   tokens (plan-compact), finish the phase, write the checkpoint at {{.EpicDir}}/handoffs/{{.ID}}.md and end your turn with
   "ready to compact"; {{.Context.CompactNow}} tokens (compact-now) means do that immediately.
6. MAILBOX AND INBOX. The leader steers you through a durable inbox on disk: {{.EpicDir}}/inbox/{{.ID}}/NNN.msg. When a
   one-line doorbell appears in your terminal, or at the start of every phase and before every `ask`: list the inbox, read
   each record in numeric order and `mv` it to `handled/` AS SOON AS YOU HAVE READ IT (the move is your acknowledgement),
   then act. ON THE ORCHESTRATION PLANE also run `orca orchestration check --json` at those moments for replies to your
   asks. ON THE TERMINAL PLANE (`COX_PLANE=terminal`) there is no `orca orchestration`: the inbox is the only channel and
   a reply to a question lands both as an inbox record and via `cox question wait` (see PLANE below).
7. CONTEXT. Everything you would need after a context reset lives on disk (plan, checkpoint), not in chat. One script per
   step, runner output piped through `tail`, never a whole-file `Write` of a file you could `Edit`.
8. EVERY DISPATCH ENDS WITH A COMPLETION SIGNAL. A leader steer that asks for follow-ups and re-verification is a re-run of
   your story: when the work is done and re-verified, report completion, do not stop on a bare progress `status`.
   ON THE ORCHESTRATION PLANE Orca allows only ONE `worker_done` per dispatch, so: the FIRST completion is `worker_done`
   (kind `worker_done`, listing the commits); EVERY LATER completion in the same dispatch is
   `orca orchestration send --type status --subject "done: <3-line summary>"` (the subject MUST start with `done:`). The
   watcher classifies a `done:` status as a completion and advances the story; a re-run that ends with only a plain
   progress `status` leaves the story idle (the watcher raises an `idle_no_done` wake).
9. PLANE. Your plane is `COX_PLANE` (default `orchestration`). ON THE TERMINAL PLANE (`COX_PLANE=terminal`): you report
   THROUGH COX, never through `orca orchestration`, and you send NO heartbeat. Progress is
   `cox story report status --note "<3 sentences>" --epic {{.EpicDir}} --story {{.ID}}`; a blocker is
   `cox story report stuck --note "..."`; completion is `cox story report done --note "<summary>" --evidence pr=<url>`
   and there is NO cap - a re-run just sends another `report done` (no `done:` status dance). You ASK with
   `cox story report question --body "<question>"` (it prints `qNNN`), then block on
   `cox question wait qNNN --max 25m` (exit 3 = timed out: checkpoint, end your turn, the leader resumes you). The
   watcher still raises `idle_no_done` if you go idle after a steer without a `report done`.
10. CODEX WORKER. When you run under the codex harness and the story asks for per-item review (the leader reviews and
    commits each item at its boundary), do NOT `spawn_agent` sub-agents to self-verify: forked sub-agents copy your whole
    context into each and cost far more than the leader's own review (the M13b dogfood burned ~1.2M tokens on three
    forked verifiers). Run the item's own focused tests yourself and let the leader review. Write your checkpoint at
    {{.EpicDir}}/handoffs/{{.ID}}.md after EACH item boundary (codex `checkpoint=manual`: no PreCompact hook writes it
    for you), so a resume never loses a completed item.
11. NO LOCAL DIALOGS. Every ruling and question goes ONLY through `cox story report question` + `cox question wait`
    (orchestration plane: `orca orchestration ask`). NEVER ask through a harness dialog - AskUserQuestion, a permission
    prompt, `/ask` - it is invisible to cox: the watcher cannot see it, the leader never receives it, and your turn
    stalls on a dialog no one can answer. If a tool tries to open one, cancel it and report the question through cox.
